Investment Decision Operating System (IDOS)
Software Design Document (SDD)
12: System Architecture - State Machine & Event-Driven Pipeline
Versión: 1.2
Estado: Aprobado

1. Objetivo
Describir la máquina de estados que gobierna el ciclo de vida de una `Opportunity`, el flujo de datos a través del pipeline de Workers y el modelo de dominio sobre el que operan.

2. Máquina de Estados (State Machine)
El modelo central de dominio es la `Opportunity`. Su ciclo de vida sigue una máquina de estados lineal y persistida en SQLite:

    ┌──────────┐
    │ Pending  │ (Nueva oportunidad disponible para asignación)
    └────┬─────┘
         ▼
    ┌──────────┐
    │ InReview │ (Worker asignado, análisis en progreso)
    └────┬─────┘
         ▼
    ┌──────────┐
    │ Reviewed │ (Análisis completado, pendiente de decisión del Board)
    └────┬─────┘
         ├──────────────────┐
         ▼                  ▼
    ┌──────────┐    ┌──────────────┐
    │ Approved │    │  Rejected    │
    └────┬─────┘    │ (with cause) │
         │          └──────────────┘
         ▼
    ┌───────────┐
    │ Executing │ (Ejecutándose en mercado real)
    └─────┬─────┘
           ├────────────────────┐
           ▼                    ▼
    ┌──────────┐        ┌──────────────┐
    │  Closed  │        │   Failed     │
    │ (Profit) │        │ (with cause) │
    └──────────┘        └──────────────┘

Toda transición se registra en la tabla `state_transitions` con sello de tiempo y agente responsable.

3. Modelo de Datos Central (SQLite)
El sistema persiste 6 tablas principales en una base de datos SQLite única:

3.1 Tabla `opportunities`
- opportunity_id (TEXT PK)
- ticker (TEXT)
- title (TEXT)
- status (TEXT: Pending | InReview | Reviewed | Approved | Rejected | Executing | Closed | Failed)
- assigned_worker (TEXT)
- entry_price (REAL)
- stop_loss (REAL)
- take_profit (REAL)
- conviction (REAL 0.0-1.0)
- created_at (TEXT ISO8601)
- updated_at (TEXT ISO8601)

3.2 Tabla `state_transitions`
- transition_id (TEXT PK)
- opportunity_id (TEXT FK)
- from_status (TEXT)
- to_status (TEXT)
- reason (TEXT)
- agent (TEXT)
- created_at (TEXT ISO8601)

3.3 Tabla `event_log`
- event_id (TEXT PK)
- event_type (TEXT)
- source (TEXT)
- payload (TEXT JSON)
- created_at (TEXT ISO8601)

3.4 Tabla `provenance_chain`
- chain_id (TEXT PK)
- conclusion_id (TEXT)
- evidence_id (TEXT)
- evidence_type (TEXT)
- source (TEXT)
- timestamp (TEXT ISO8601)
- metadata (TEXT JSON)

3.5 Tabla `telemetry_runs`
- run_id (TEXT PK)
- worker_name (TEXT)
- start_time (TEXT ISO8601)
- end_time (TEXT ISO8601)
- status (TEXT)
- tokens_used (INTEGER)
- error (TEXT)

3.6 Tabla `checkpoints`
- checkpoint_id (TEXT PK)
- run_id (TEXT FK)
- scope (TEXT)
- state (TEXT JSON)
- created_at (TEXT ISO8601)

4. Event Bus
Arquitectura punto a punto con un bus de eventos. El bus de eventos es un singleton en memoria con almacenamiento opcional en la tabla `event_log`. Los Workers se suscriben mediante `event_bus.subscribe(event_type, callback)` y publican eventos para comunicarse de forma asíncrona.

Tipos de evento definidos:
- `CommitRequest`: Solicita a GitQueueWorker la escritura de nuevo conocimiento.
- `DataIngested`: Nuevo dato disponible para análisis.
- `AnalysisReady`: Worker ha completado análisis.
- `DecisionMade`: Board ha tomado una decisión.
- `Notification`: Alerta para el usuario.

5. SDK Harness Integration
Los Workers que se ejecutan como agentes externos a través de `AgentBase` reciben automáticamente suscripción al Event Bus y notificaciones de ciclo de vida. El `RunManifest` se crea en `BaseWorker.execute()` antes de delegar al método concreto del Worker.
