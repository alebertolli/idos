Investment Decision Operating System (IDOS)
Software Design Document (SDD)
16: Resilience & Reliability Architecture
Versión: 1.1
Estado: Aprobado

1. Objetivo
Definir la arquitectura de resiliencia y fiabilidad del IDOS, consolidada en un único módulo `idos.resilience`.

2. Principios
2.1 Módulo Único: Toda la resiliencia se centraliza en `idos-core/idos/resilience/`. No hay módulo `reliability/` separado.
2.2 Checkpointing Automático: Todo Worker gestiona su estado mediante RunManifest y checkpoints.
2.3 Self-Healing Delegado: Errores de parseo y recuperación se delegan al SelfHealer.
2.4 Cost Protection: El sistema puede limitar gasto en APIs externas mediante CostController.
2.5 Adaptive Routing: El sistema puede seleccionar dinámicamente el proveedor de IA basado en rendimiento histórico y requisitos de la tarea.

3. Estructura del Módulo

3.1 `idos-core/idos/resilience/__init__.py`
Re-exporta: SelfHealer, CheckpointManager, RunManifest, AdaptiveRouter, ProviderScore, TaskRequirement, CostController, CostBudget, CircuitBreaker.

3.2 `idos-core/idos/resilience/self_healing.py`
- `SelfHealer`: Clase que aplica estrategias de reparación automática (retry, fallback, parse correction).
  - Método `heal(attempt: int, error: str, context: dict) -> str`: retorna una de las estrategias: `retry`, `fallback`, `abort`, `cooldown`.
  - Método `recover_parse(raw: str, target_type: type) -> Any`: intenta recuperar parseo de JSON con correcciones progresivas.

3.3 `idos-core/idos/resilience/checkpoint.py`
- `CheckpointManager`: Gestiona puntos de control para Workers. Almacena y restaura estado en SQLite (tabla `checkpoints`).
- `RunManifest`: Manifiesto de ejecución de un Worker. Creado automáticamente en `BaseWorker.execute()`.
  - Almacena worker_name, timestamps, status, tokens_used, error.
  - Persiste en SQLite (tabla `telemetry_runs`).
  - Emite notificación al NotificationCenter al completar (success/partial/failure).

3.4 `idos-core/idos/resilience/adaptive.py`
- `AdaptiveRouter`: Selecciona dinámicamente proveedor LLM basado en scoring histórico.
- `ProviderScore`: Almacena métricas de rendimiento por proveedor.
- `TaskRequirement`: Define requisitos de una tarea (modo, max_tokens, categoría).

3.5 `idos-core/idos/resilience/cost_control.py`
- `CostController`: Controla y limita gasto en APIs de LLM.
- `CostBudget`: Define presupuesto por período (diario, semanal, mensual, ticker).

3.6 Circuit Breaker
Implementado internamente en `ai/llm.py`. Estado: `CLOSED` → `OPEN` → `HALF_OPEN`. Se abre tras 3 fallos consecutivos en un intervalo de 60 segundos.

4. Integración con LLMClient
El `SelfHealer` se delega en el método `_parse_json()` de `LLMClient` (`idos-core/idos/ai/llm.py`). Cuando el parseo JSON falla:
1. Se invoca `SelfHealer.recover_parse()` que intenta correcciones progresivas.
2. Si falla la recuperación, se invoca `SelfHealer.heal()` para determinar estrategia.
3. Las estrategias posibles son: retry (reintentar con el mismo prompt), fallback (usar modelo alternativo), cooldown (esperar), abort (fallar definitivamente).

5. Checkpointing y RunManifest
El `BaseWorker.execute()` en `idos-core/idos/workers/base.py`:
1. Crea un `RunManifest` y lo persiste en SQLite.
2. Ejecuta el método concreto del Worker (e.g., `research_worker.analyze()`).
3. Al completar, actualiza el RunManifest con estado (success/partial/failure) y tokens consumidos.
4. Emite notificación vía NotificationCenter.

En caso de fallo, el worker publica un evento de tipo `Notification` con severidad `error`. En caso de éxito parcial, publica `warning`.
