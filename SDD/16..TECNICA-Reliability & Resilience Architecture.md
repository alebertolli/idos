Reliability & Resilience Architecture

1. Objetivo

Este documento define la arquitectura de resiliencia del Investment Decision Operating System (IDOS).

Su objetivo es garantizar que el sistema pueda operar durante largos períodos de tiempo con mínima intervención humana, tolerando fallos temporales de infraestructura, proveedores externos y modelos de IA, sin comprometer la integridad del conocimiento ni la continuidad del proceso de inversión.

La filosofía del sistema es:

Nunca perder conocimiento. Nunca perder trabajo. Nunca detener el sistema por un fallo recuperable.

2. Principios

Toda decisión relacionada con confiabilidad debe respetar estos principios.

2.1 Knowledge First

El conocimiento generado es el activo más valioso.

Antes de abortar un proceso, el sistema debe intentar preservar toda la información ya producida.

2.2 Automatic Recovery

Los errores recuperables deben resolverse automáticamente.

La intervención humana debe ser la excepción.

2.3 Graceful Degradation

Si un componente falla, el sistema debe continuar utilizando capacidades reducidas antes que detenerse.

2.4 Human Attention is Scarce

Las alertas deben ser pocas, relevantes y accionables.

Nunca generar ruido innecesario.

2.5 Observable by Default

Toda ejecución debe ser completamente trazable.

14. Estados de ejecución

Todos los Workers finalizan en uno de estos estados.

Todo el trabajo fue completado.

Interrumpido manualmente.

## 15. Observabilidad

Toda ejecución del IDOS registra sus trazas a través de la interfaz unificada `sdk.telemetry.trace()`. Esta interfaz es el único punto de contacto de los Workers con el sistema de observabilidad.

**Backend actual**: SQLite local (tabla `telemetry_traces`). Simple, sin dependencias.
**Backend futuro**: la misma interfaz puede redirigir a Langfuse, OpenTelemetry o Arize cambiando únicamente la configuración del SDK, sin modificar ningún Worker.

### 15.1 Métricas Registradas por Ejecución
Cada llamada a `sdk.telemetry.trace()` persiste los siguientes campos:

| Campo | Descripción |
| :--- | :--- |
| `run_id` | Identificador único de la ejecución |
| `worker` | Nombre del Worker |
| `step` | Etapa del proceso (`LLM_CALL`, `DATA_FETCH`, `STATE_TRANSITION`, `GIT_COMMIT`) |
| `provider` | Proveedor de LLM utilizado (si aplica) |
| `prompt_id` | Identificador del prompt del Prompt Registry |
| `tokens_in` / `tokens_out` | Consumo de tokens |
| `latency_ms` | Latencia de la operación |
| `status` | `SUCCESS`, `RETRY`, `FAILOVER`, `FAILED` |
| `detail` | Información adicional libre (causa de error, estado de transición, etc.) |

17. Health Checks

El SDK ejecuta verificaciones antes de iniciar un Worker.

Validaciones mínimas:

conexión Git
acceso SQLite
disponibilidad de proveedores LLM
acceso a fuentes financieras
espacio en disco
configuración válida

Si falla una validación crítica, el Worker no inicia.

20. Cost Protection

El sistema controla el consumo de recursos.

Incluye:

límite de tokens por Worker
límite diario por proveedor
límite mensual configurable
tiempo máximo de ejecución
tamaño máximo de contexto

Cuando un límite es alcanzado:

cambiar proveedor
resumir contexto
dividir trabajo
posponer ejecución

Nunca consumir recursos ilimitadamente.
