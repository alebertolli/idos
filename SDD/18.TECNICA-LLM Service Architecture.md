Investment Decision Operating System (IDOS)
Software Design Document (SDD)
Documento 18: LLM Service Architecture
Versión: 1.7
Estado: Aprobado

1. Objetivo
Definir la arquitectura del servicio centralizado de acceso a Large Language Models (LLM) en IDOS. El `LLMService` es el único punto de entrada para toda interacción con LLMs, reemplazando la creación directa de `LLMClient` por parte de los Workers.

2. Principios
- Single Source of Truth: La configuración de proveedores, modelos, rate limits y circuit breakers se define en `idos-config/models.yml` y se carga una única vez.
- AI Agnostic: Los Workers no conocen qué proveedor o modelo se usa. Solo expresan un `task_type` (reasoning, analysis, classification, extraction).
- Resiliencia por Capas: Rate limiter → Circuit breaker → fallback transitorio intra-provider → failover entre providers. Un 402/429 no repite modelos del mismo provider; el servicio conserva metadatos del límite y continúa con otro provider apto.
- Observabilidad: Toda llamada LLM registra trazas con provider, modelo, tokens, latencia y status.
- API-compatible con LLMClient: `LLMService.generate()` y `LLMService.generate_structured()` tienen la misma firma que `LLMClient`, permitiendo migración gradual.

4. Flujo de llamada

Worker → LLMService.generate(prompt, task_type="reasoning")
  │
  ├─ 1. Rank providers: hint → AdaptiveRouter → fallback_order → resto
  │
  ├─ 2. For each provider:
  │     ├─ CircuitBreaker.is_available? → NO → skip
  │     ├─ RateLimiter.allow("provider:rpm")? → NO → skip
  │     ├─ RateLimiter.allow("provider:rpd")? → NO → skip
  │     ├─ LLMClient.generate() (fallback intra-provider solo en fallas transitorias; 402/429 no reintentan)
  │     ├─ Success? → AdaptiveRouter.record_success + CircuitBreaker.reset → return
  │     └─ Failure? → AdaptiveRouter.record_failure + CircuitBreaker.record
  │                   → 402/429 bloquea provider en esta corrida; otro error permite failover
  │
  └─ 3. All failed? → return LLMResponse(success=False, error)

5. Configuración (idos-config/models.yml)

```yaml
llm:
  default_provider: gemini
  providers:
    gemini:
      model: gemini-3.8-flash
      fallback: gemini-3.7-flash
      rpm: 60
      rpd: 1500
      task_types:
        - reasoning
        - analysis
        - classification
        - research
    groq:
      model: openai/gpt-oss-120b
      fallback: openai/gpt-oss-20b
      rpm: 30
      rpd: 1000
      task_types:
        - reasoning
        - analysis
        - research
    openrouter:
      model: google/gemma-4-31b-it:free
      rpm: 20
      rpd: 50
      task_types:
        - reasoning
        - analysis
        - classification
      disabled_task_types:
        - research
  fallback_order:
    - provider: groq
      model: openai/gpt-oss-120b
      fallback_model: openai/gpt-oss-20b
    - provider: openrouter
      model: google/gemma-4-31b-it:free
  circuit_breaker:
    failure_threshold: 3
    recovery_timeout: 60
  max_tokens_per_worker: 100000
  max_daily_tokens: 1000000
```

Campos por provider:
- `model`: Modelo primario
- `fallback`: Modelo alternativo dentro del mismo provider para fallas 404/408/5xx; los 402/429 bloquean al provider en la corrida actual
- `rpm`: Límite de requests por minuto
- `rpd`: Límite de requests por día
- `task_types`: Tipos de tarea aptos para AdaptiveRouter; `disabled_task_types` excluye explícitamente tareas
- Los RPM/RPD son límites configurados para el cliente; no sustituyen los límites reales por proyecto, modelo, plan o cuenta del proveedor. Al agotarse un límite local, el provider se omite y expone el tiempo restante de ventana.
- `max_tokens_per_worker` y `max_daily_tokens` figuran en configuración, pero todavía no se aplican como presupuestos de tokens en runtime.

6. Task Types

| Tipo | Uso | Ejemplo |
|------|-----|--------|
| `reasoning` | Análisis complejo no estructurado de Research | DDD, AOIF |
| `analysis` | Síntesis JSON de Research y documentación | Hipótesis, Wiki |
| `classification` | Clasificación de documentos para Research | Categorización de fuentes |
| `research` | Investigación de oportunidades | DDD, Wiki y AOIF |

7. Integración con Workers

Cada Worker recibe el LLMService a través de `config.get("llm_service")` en lugar de crear su propio `LLMClient`:

```python
class ResearchWorker(BaseWorker):
    def __init__(self, config):
        super().__init__(config)
        self.llm = config.get("llm_service") or LLMClient(...)
```

Si no se provee `llm_service` (ej: tests que usan mock), el Worker crea un `LLMClient` como fallback para mantener compatibilidad hacia atrás.

8. Creación en pipelines

En GitHub Actions se crea una única instancia de `LLMService` y se pasa a todos los Workers:

```python
from idos.ai.service import LLMService
llm_svc = LLMService("idos-config/models.yml")
worker = ResearchWorker({"llm_service": llm_svc, "prompts_path": "..."})
```

9. LLMClient (capa de transporte)

`LLMClient` se mantiene como la capa de transporte para un único provider. Sus responsabilidades:
- Llamada HTTP al endpoint del provider
- Captura `Retry-After` numérico/HTTP date y ventanas `x-ratelimit-*`, incluidos resets en duraciones de Groq
- Para 402/429 falla inmediatamente y deja que `LLMService` pruebe otro provider; no espera ni repite modelos del provider agotado
- Fallback intra-provider a `fallback_model` para errores transitorios 404/408/5xx; errores de cliente no reintentables conservan fail-fast.

No realiza cross-provider failover — eso es responsabilidad de `LLMService`.

10. Rate Limiting

El sistema mantiene dos rate limiters por provider:
- **RPM**: RateLimiter con window=60s, max_calls=config.rpm
- **RPD**: RateLimiter con window=86400s, max_calls=config.rpd

Si un provider excede su límite, se salta automáticamente y se prueba el siguiente. Los límites se resetean solos al vencer la ventana.

11. Circuit Breaker

- **CLOSED**: Funcionamiento normal. Tras `failure_threshold` fallos consecutivos → OPEN.
- **OPEN**: Se salta el provider por `recovery_timeout` segundos. Luego → HALF_OPEN.
- **HALF_OPEN**: Se permite un request. Si éxito → CLOSED. Si falla → OPEN.

12. Métricas y Observabilidad

`LLMService.health()` retorna estado de todos los providers:

```python
{
  "gemini": {
    "model": "gemini-2.0-flash",
    "circuit": "closed",
    "rpm_remaining": 58,
    "rpd_remaining": 1420,
    "limits": {"rpm": 60, "rpd": 1500}
  },
  "groq": {...},
  "openrouter": {...}
}
```

Las respuestas conservan provider, status HTTP, `Retry-After`, tokens restantes y reset. Research persiste diagnóstico de capacidad en `cache/ddd_results.json`; ante agotamiento de todos los providers conserva pendientes en `cache/ddd_research_resume.json`, procesa como máximo cinco oportunidades automáticas por corrida y las reanuda diariamente. Los resultados programados viajan por una rama y PR; CI se ejecuta antes de solicitar auto-merge. Las trazas generales siguen el sistema de telemetría (SDD-16.15.1).

13. Workers que consumen LLMService

| Worker | Uso de LLM |
|--------|-----------|
| ResearchWorker | DDD, Hypothesis, AOIF, Wiki |
| AssessmentPipeline (DDD Step 3-7) | _(no LLM, 100% algorítmico)_ |
| PostMortemWorker | _(sin LLM; análisis determinista de outcomes y evidencia)_ |
| DecisionBoardWorker | _(shim `SKIPPED`; sin LLM ni mutación)_ |

> **Estado actual**: `DecisionBoardWorker` se conserva como shim de compatibilidad y
> siempre devuelve `SKIPPED`; no lee ni modifica oportunidades, no persiste decisiones
> y no llama al `LLMService`. La implementación revisada antes de este cambio tampoco
> contenía `_llm_evaluate`: ejecutaba reglas deterministas, pero podía cambiar estados
> automáticamente usando valores por defecto para engines ausentes y asimetría. El
> `AssessmentPipeline` es determinista y persiste una propuesta pendiente; una aprobación
> atribuible del gestor se registra por `Decision Review`.

> **Especificación**: El filtro de entrada es **100% algorítmico** y no depende de proveedores LLM.
> El `EntryMonitorWorker` y el `WyckoffAnalyzer` (indicador compuesto de oferta/demanda) se
> implementan de forma determinista (SDD-9 §5). El `task_type` `classification` queda disponible
> para otros consumidores que no sean el filtro de entrada.

13.1 Respuestas JSON estructuradas

Cuando un Research solicita una respuesta JSON, el servicio transmite
`responseMimeType=application/json` a Gemini, concatena todas las partes de
texto devueltas y verifica `finishReason`. Un motivo de finalización diferente
de `STOP` se trata como respuesta incompleta para habilitar el fallback y evitar
que contenido truncado avance a persistencia. Si la respuesta sigue sin validar,
el log registra longitud, línea, columna y causa de parsing sin imprimir el
contenido completo; Research se detiene sin reemplazar el análisis vigente.
Otros proveedores reciben la instrucción JSON estándar y permanecen sujetos al
mismo gate de parsing y a la validación de contrato del ResearchWorker.

## Addendum 2026-09-10 — Deterministic strategy evaluation

Momentum, límites, correlación, liquidez, sizing, fallback y gates patrimoniales se evalúan determinísticamente. El LLM queda reservado para Research no estructurado, síntesis y casos ambiguos; no puede superar reglas duras.
