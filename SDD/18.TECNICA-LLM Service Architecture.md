Investment Decision Operating System (IDOS)
Software Design Document (SDD)
18: LLM Service Architecture
Versión: 1.0
Estado: Aprobado

1. Objetivo
Definir la arquitectura del servicio centralizado de acceso a Large Language Models (LLM) en IDOS. El `LLMService` es el único punto de entrada para toda interacción con LLMs, reemplazando la creación directa de `LLMClient` por parte de los Workers.

2. Principios
- Single Source of Truth: La configuración de proveedores, modelos, rate limits y circuit breakers se define en `idos-config/models.yml` y se carga una única vez.
- AI Agnostic: Los Workers no conocen qué proveedor o modelo se usa. Solo expresan un `task_type` (reasoning, analysis, classification, extraction).
- Resiliencia por Capas: Retry → Intra-provider fallback → Rate limiter → Circuit breaker → Cross-provider failover.
- Observabilidad: Toda llamada LLM registra trazas con provider, modelo, tokens, latencia y status.
- API-compatible con LLMClient: `LLMService.generate()` y `LLMService.generate_structured()` tienen la misma firma que `LLMClient`, permitiendo migración gradual.

4. Flujo de llamada

Worker → LLMService.generate(prompt, task_type="reasoning")
  │
  ├─ 1. Rank providers: hint → AdaptiveRouter → fallback_order → resto
  │
  ├─ 2. For each provider:
  │     ├─ CircuitBreaker.is_available? → NO → skip
  │     ├─ RateLimiter.allow("provider:rpm")? → NO → skip
  │     ├─ RateLimiter.allow("provider:rpd")? → NO → skip
  │     ├─ LLMClient.generate() (con retry interno + intra-provider fallback)
  │     ├─ Success? → AdaptiveRouter.record_success + CircuitBreaker.reset → return
  │     └─ Failure? → AdaptiveRouter.record_failure + CircuitBreaker.record
  │                   → sleep(2s) → try next provider
  │
  └─ 3. All failed? → return LLMResponse(success=False, error)

5. Configuración (idos-config/models.yml)

```yaml
llm:
  default_provider: gemini
  providers:
    gemini:
      model: gemini-2.0-flash
      fallback: gemini-flash-latest
      rpm: 60
      rpd: 1500
      task_types:
        - reasoning
        - analysis
        - classification
    groq:
      model: llama-3.3-70b-versatile
      fallback: llama-3.1-8b-instant
      rpm: 30
      rpd: 1000
      task_types:
        - reasoning
        - analysis
    openrouter:
      model: google/gemma-4-31b-it:free
      fallback: openrouter/free
      rpm: 20
      rpd: 50
      task_types:
        - reasoning
        - analysis
        - classification
  fallback_order:
    - provider: groq
      model: llama-3.3-70b-versatile
      fallback_model: llama-3.1-8b-instant
    - provider: openrouter
      model: google/gemma-4-31b-it:free
      fallback_model: openrouter/free
  circuit_breaker:
    failure_threshold: 3
    recovery_timeout: 60
  max_tokens_per_worker: 100000
  max_daily_tokens: 1000000
```

Campos por provider:
- `model`: Modelo primario
- `fallback`: Modelo alternativo dentro del mismo provider (se usa cuando el primario da 429)
- `rpm`: Límite de requests por minuto
- `rpd`: Límite de requests por día
- `task_types`: Tipos de tarea para los que este provider es apto (usado por AdaptiveRouter)

6. Task Types

| Tipo | Uso | Ejemplo |
|------|-----|--------|
| `reasoning` | Análisis complejo multi-paso | DDD, AOIF |
| `analysis` | Evaluación estructurada | Board, Post-Mortem |
| `classification` | Clasificación de patrones | Categorización de documentos |

7. Integración con Workers

Cada Worker recibe el LLMService a través de `config.get("llm_service")` en lugar de crear su propio `LLMClient`:

```python
class ResearchWorker(BaseWorker):
    def __init__(self, config):
        super().__init__(config)
        self.llm = config.get("llm_service") or LLMClient(...)
```

Si no se provee `llm_service` (ej: tests que usan mock), el Worker crea un `LLMClient` como fallback para mantener compatibilidad hacia atrás.

8. Creación en pipelines

En GitHub Actions se crea una única instancia de `LLMService` y se pasa a todos los Workers:

```python
from idos.ai.service import LLMService
llm_svc = LLMService("idos-config/models.yml")
worker = ResearchWorker({"llm_service": llm_svc, "prompts_path": "..."})
```

9. LLMClient (capa de transporte)

`LLMClient` se mantiene como la capa de transporte para un único provider. Sus responsabilidades:
- Llamada HTTP al endpoint del provider
- Retry con backoff y header `Retry-After` (4s, 8s, 16s)
- Si `Retry-After > 120s`, falla inmediatamente sin esperar (fuerza failover al siguiente provider)
- Fallback intra-provider a `fallback_model` en caso de 429 o 404 (funciona para todos los providers)

No realiza cross-provider failover — eso es responsabilidad de `LLMService`.

10. Rate Limiting

El sistema mantiene dos rate limiters por provider:
- **RPM**: RateLimiter con window=60s, max_calls=config.rpm
- **RPD**: RateLimiter con window=86400s, max_calls=config.rpd

Si un provider excede su límite, se salta automáticamente y se prueba el siguiente. Los límites se resetean solos al vencer la ventana.

11. Circuit Breaker

- **CLOSED**: Funcionamiento normal. Tras `failure_threshold` fallos consecutivos → OPEN.
- **OPEN**: Se salta el provider por `recovery_timeout` segundos. Luego → HALF_OPEN.
- **HALF_OPEN**: Se permite un request. Si éxito → CLOSED. Si falla → OPEN.

12. Métricas y Observabilidad

`LLMService.health()` retorna estado de todos los providers:

```python
{
  "gemini": {
    "model": "gemini-2.0-flash",
    "circuit": "closed",
    "rpm_remaining": 58,
    "rpd_remaining": 1420,
    "limits": {"rpm": 60, "rpd": 1500}
  },
  "groq": {...},
  "openrouter": {...}
}
```

Las trazas de cada llamada se registran vía el sistema de telemetría (SDD-16.15.1).

13. Workers Migrados

| Worker | Archivo | Uso de LLM |
|--------|---------|-----------|
| ResearchWorker | `workers/ai/research_worker.py` | DDD, Hypothesis, AOIF, Wiki |
| DecisionBoardWorker | `workers/ai/decision_board_worker.py` | Board evaluation |
| PostMortemWorker | `workers/learning/post_mortem_worker.py` | Post-mortem analysis |
| LLMWorker | `workers/ai/llm_worker.py` | Generic prompt execution |

> **Nota (v1.2)**: `EntryMonitorWorker` y `WyckoffAnalyzer` dejaron de consumir LLM. La clasificación de fase de entrada se implementa ahora mediante el **indicador compuesto algorítmico** (SDD-9 §5) 100% determinista, sin dependencia de proveedores LLM. El `task_type` `classification` sigue disponible para otros usos (no Wyckoff).
