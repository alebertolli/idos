# Investment Decision Operating System (IDOS)
## Software Design Document (SDD)
## Documento 12: Runtime Architecture - Arquitectura de Ejecución

Versión: 1.0  
Estado: Aprobado  

---

## 1. Objetivo

Este documento describe el comportamiento dinámico y el flujo de ejecución en tiempo de ejecución del **Investment Decision Operating System (IDOS)**. 

Define el ciclo de los datos desde la detección de un trigger o evento del mercado, pasando por el procesamiento de los Workers y la actualización del conocimiento, hasta la consolidación del Decision Pipeline y la notificación final en la bandeja del usuario.

---

## 2. Filosofía Reactiva

El IDOS es un sistema reactivo y orientado a eventos. No consume recursos computacionales de forma continua sin un propósito operativo; reacciona a cambios específicos y significativos. El objetivo es maximizar la eficiencia del procesamiento, reducir el consumo innecesario de tokens de LLM y evitar generar ruido de información al usuario.

---

## 3. Clasificación de Workers

Para optimizar el rendimiento y el control de costos de la API de IA, los Workers (que implementan las capacidades del sistema) se dividen en dos categorías según su naturaleza tecnológica:

### 3.1 Data Workers (Deterministas)
* **Descripción**: Procesos de software tradicionales que operan mediante reglas cuantitativas directas. No utilizan Inteligencia Artificial ni realizan llamadas a LLMs.
* **Ejemplos**: Descargar estados financieros consolidados, actualizar cotizaciones de acciones en tiempo real, parsear datos de volumen diarios, escribir registros en SQLite y sincronizar repositorios Git mediante commits automáticos.

### 3.2 AI Workers (Heurísticos)
* **Descripción**: Procesos analíticos complejos que requieren el procesamiento de lenguaje natural y razonamiento contextual utilizando LLMs a través del SDK de IDOS.
* **Ejemplos**: Analizar la alineación estratégica del *management* en las transcripciones de resultados trimestrales, estructurar hipótesis, valorar riesgos competitivos cualitativos, redactar informes de Post Mortem e interpretar eventos de noticias corporativas.

---

## 4. Tipos de Disparadores (Triggers)

El sistema inicia la ejecución de sus procesos bajo dos tipos de desencadenantes del **Event Bus**:

### A. Scheduled Triggers (Temporales)
Ocurren por planificación horaria o de calendario.
* *Ejemplos*: El Scout semanal de empresas, la revisión mensual de convicción del portfolio, el rebalanceo de cartera y la calibración nocturna del modelo.

### B. Event Triggers (Eventos de Negocio)
Ocurren reactivamente cuando se detecta una variación relevante en el mundo exterior o interno del sistema.
* *Ejemplos*: Publicación de un nuevo reporte financiero (10-Q/10-K), cambio del CEO de un activo vigilado, entrada de una cotización en zona de compra u ocurrencia de una alerta de riesgo.

---

## 5. El Decision Pipeline

El **Decision Pipeline** es el proceso lógico central que ejecuta el **Decision Orchestrator** para resolver si un evento del mercado requiere una alteración del portfolio:

```
[Trigger / Evento del Bus]
           │
           ▼
Etapa 1: Clasificación del Evento (Financiero, Técnico, Regulatorio, etc.)
           │
           ▼
Etapa 2: Análisis de Relevancia (¿Afecta a alguna hipótesis activa?)
           │
      No ──┼────────► Registrar en logs pasivos y finalizar
           │
          Sí
           ▼
Etapa 3: Impacto (Se actualiza la Knowledge Base y se recalculan Assessments)
           │
           ▼
Etapa 4: Decision Orchestration (Se inyectan las Rules a los Assessments)
           │
           ▼
Etapa 5: Propuesta de Decisión (Requiere Board / Telegram / Decision Inbox)
```

## 7. Control de Concurrencia, Estado y Tolerancia a Fallos

### 7.1 Git Commit Queue (Serialización de Escrituras)
Ningún Worker realiza `git push` directamente. El flujo es el siguiente:

```
Worker (finaliza su tarea)
       │
       │ publica evento
       ▼
CommitRequest (Event Bus)
       │
       │ registra en SQLite
       ▼
Commit Queue (tabla `pending_commits` en SQLite)
       │
       │ el único proceso autorizado lee la cola
       ▼
Git Commit Manager Worker
       │
       ▼
    git push → idos-knowledge
```

Este diseño elimina los conflictos de concurrencia. El `Git Commit Manager` es un Data Worker liviano que procesa la cola periódicamente (ej. cada 5-10 minutos). Puede agrupar múltiples archivos modificados en un único commit atómico con un mensaje descriptivo.

### 7.2 State Machine de Oportunidades (SQLite)
El ciclo de vida de cada `Opportunity` es una máquina de estados lineal registrada en SQLite. No requiere librerías externas de orquestación.

```
NEW
 │
 ▼SCOUTED
 │
 ▼UNDER_RESEARCH
 │
 ▼BOARD_PENDING
 │
 ▼BUYLIST
 │
 ▼POSITION_OPEN
 │
 ▼MONITORING
 │
 ▼EXITED
 │
 ▼POSTMORTEM
 │
 ▼ARCHIVED
```

Cada transición queda registrada con `timestamp`, `worker_name` y `cause`. Si un proceso se interrumpe, el scheduler identifica las oportunidades atascadas en un estado intermedio y reactiva el Worker correspondiente sin intervención humana.

### 7.3 Manejo de Errores del LLM y Failover
El sistema utiliza un `LLMService` centralizado (`idos.ai.service.LLMService`) como único punto de acceso a LLMs. Todos los Workers obtienen su `LLMService` desde el contexto compartido, no crean `LLMClient` directamente.

El `LLMService` gestiona automáticamente:
- **Selección de proveedor**: Ordenado por hint explícito → AdaptiveRouter (mejor proveedor según historial de éxito/latencia) → fallback_order de configuración → resto de proveedores.
- **Rate limiting**: Respeta RPM (requests per minute) y RPD (requests per day) por proveedor, configurado en `models.yml`.
- **Circuit breaker**: Si un proveedor falla N veces seguidas (configurable, default 3), se salta por 60 segundos.
- **Reintento con backoff**: Respeta header `Retry-After` del proveedor. Backoff 4s, 8s, 16s.
- **Failover intra-provider**: Si un modelo específico da 429, intenta el `fallback_model` del mismo proveedor (ej: 70B→8B en Groq, 2.5→2.0 en Gemini) antes de cambiar de proveedor.
- **Adaptive routing**: `AdaptiveRouter` trackea success rate y latencia por proveedor para mejorar selección futura.
- **Telemetría automática**: Cada llamada registra provider, modelo, tokens, latencia, status.

Ver SDD-18 para diseño detallado del LLMService.

### 7.4 Auto-Healing de Formato
Cuando un LLM retorna un esquema JSON o Markdown que no valida con el esquema estricto (Pydantic), el SDK ejecuta un sub-prompt rápido de reparación antes de arrojar un error de parsing.
